## Context

CF/EDT-формы индексируются функцией `_collect_form_elements()` в единую
таблицу `form_elements`; `parse_form()` группирует её строки и возвращает
обработчики, команды, атрибуты и `module_path`. Для `v8unpack` эта таблица
остаётся пустой.

Форма `v8unpack` хранится обязательной JSON-тройкой и необязательным модулем:

- `<Kind>Form.json` — заголовок и позиционный массив формы;
- `<Kind>Form.elem.json` — удобные проекции `props`, `commands`, `tree` и
  позиционные `raw`;
- `<Kind>Form.id.json` — идентичность формы;
- `<Kind>Form.obj.bsl` — необязательный модуль формы.

Имена ключей `props`, `commands` и `tree` удобны для навигации, но не являются
достаточным доказательством семантики обработчиков и типов. Управляемые формы
доказываются парной XML↔JSON-выгрузкой одного CF. Обычные формы штатно
выгружаются как непрозрачный `Form.bin`, поэтому для них выбран отдельный
платформенный пробник.

## Goals / Non-Goals

**Goals:**

- получить для управляемых форм те же строки `form_elements`, что из XML, а
  для обычных — те же канонические факты, что фиксирует платформенный пробник;
- сохранить публичную форму ответа `parse_form()`;
- поддержать закрытый живой инвентарь семейств для пары `1.2.9/802`;
- обеспечить одинаковый результат полной и инкрементальной индексации;
- сохранить безопасную частичность на неизвестной форме JSON.

**Non-Goals:**

- универсально декодировать любые версии форм 1С;
- индексировать визуальную геометрию, картинки, стили и полное дерево интерфейса;
- менять BSL-анализ модуля формы;
- угадывать обработчик по совпадению имени процедуры;
- менять контракты CF/EDT.

## Decisions

### Отдельный адаптер, общая таблица

Добавляется форматный сборщик JSON-форм, возвращающий существующие 14-полевые
строки `_FORM_ELEMENTS_INSERT`. После безопасного чтения обязательной тройки и
выбора поддержанного контракта он создаёт служебную строку `kind="form"`;
поэтому подтверждённая форма без обработчиков, команд и атрибутов не исчезает.
Неподдержанная или повреждённая форма маркер не получает и по-прежнему даёт
`[]`. `_group_form_rows` уже создаёт группу до разбора `kind` и может
проигнорировать тело маркера. Новая таблица и новый публичный хелпер не нужны:
`parse_form()` уже имеет нужный контракт и приоритет индексного пути.

Альтернатива — разбирать JSON непосредственно в `parse_form()` — отклонена:
она дублировала бы полную/инкрементальную сборку и оставляла бы граф триггеров
без строк `form_elements`.

### Закрытая матрица путей и версий

Для корневой пары `v8unpack=1.2.9 / obj_version=802` живой инвентарь
`tn_bp20_custom_mcp` содержит 4 037 форм с локальными `obj_version`
`5`, `7`, `9`, `12`, `13`. Разрешены только следующие пары каталогов:

| Семейство | Каталог формы |
|---|---|
| `AccountingRegister` | `AccountingRegisterForm` |
| `AccumulationRegister` | `AccumulationRegisterForm` |
| `Catalog` | `CatalogForm` |
| `ChartOfAccounts` | `ChartOfAccountsForm` |
| `ChartOfCalculationTypes` | `ChartOfCalculationTypesForm` |
| `ChartOfCharacteristicType` | `ChartOfCharacteristicTypeForm` |
| `DataProcessor` | `Form` |
| `Document` | `DocumentForm` |
| `DocumentJournal` | `DocumentJournalForm` |
| `Enum` | `EnumForm` |
| `ExchangePlan` | `ExchangePlanForm` |
| `FilterCriterion` | `FilterCriterionForm` |
| `InformationRegister` | `InformationRegisterForm` |
| `Report` | `ReportForm` |
| `CommonForm` | сама форма: `CommonForm/<Form>/CommonForm.*` |

Первые четырнадцать семейств используют путь
`<Kind>/<Object>/<FormDir>/<Form>/<FormDir>.*`. Реестр переиспользует
существующее каноническое отображение категорий v8unpack и не выводит имя
каталога эвристически.

Основной, `.elem.json` и `.id.json` проверяются как обычные файлы внутри корня;
символьные ссылки и выход из корня запрещены. Каталог и имена владельца/формы
считаются идентичностью, а JSON обязан с ними совпасть. Поле `file` хранит путь
`*Form.elem.json`. `module_path` получается точной заменой `.elem.json` на
`.obj.bsl`, если соседний обычный файл существует внутри корня; иначе остаётся
пустым. Локальная версия формы выбирается отдельно от корневой версии
конфигурации, без выбора ближайшего контракта.

Чтение переиспользует существующий `read_v8unpack_json`: проверку разрешённого
пути, запрет символьных ссылок, обычного файла и предел 16 МиБ. Отдельный
форменный загрузчик JSON не создаётся.

### Двухконтурное доказательство форм

Позиции и UUID-теги регистрируются только после доказательства той же формы.
Для управляемых форм репозиторный оракул нормализует XML и JSON в строки
`form_elements` без `file` и сравнивает мультимножества.

Для обычных `Form.bin` отдельный платформенный пробник работает в одноразовой
локальной файловой базе, загруженной из того же CF. Пробник не входит в
сервер, индексатор или пакет времени выполнения. Он:

1. открывает зафиксированный набор обычных форм штатным клиентом 1С;
2. снимает доступные во время выполнения имена, виды, пути данных, реквизиты и
   команды;
3. выполняет зафиксированные действия и события, а инструментированная копия
   модулей форм записывает реально вызванные обработчики;
4. сохраняет канонические строки ожидаемого `form_elements` и журнал покрытия.

Инструментирование выполняется только в копии проверочной базы после фиксации
SHA-256 исходного CF; исходный CF и JSON-выгрузка не изменяются. Для каждой
проверяемой связи событие/обработчик журнал обязан содержать фактический вызов,
а не только наличие одноимённой процедуры. Невоспроизводимое действие не
считается доказанным, регистрируется как недоказанный фрагмент и не может
исчезнуть из приёмочного отчёта.

Оба контура отдельно проверяют:

- обработчики формы и элементов: scope, element, type, event, handler,
  data_path;
- команды: name и action;
- атрибуты: name, types, main, main_table, query_text;
- точный путь JSON, существование или отсутствие `*Form.obj.bsl` и ожидаемый
  `module_path`.

Манифест фиксирует SHA-256 исходного CF и пробника, версии платформы и
`v8unpack`, точные команды, хеши прочитанных XML/JSON-деревьев и журнала
пробника, покрытые корневую/локальные версии, семейства и формы элементов.
Автономная проверка манифеста подтверждает хеши сохранённых канонических
проекций без исходной большой выгрузки; большие выгрузки и файловая база в
репозиторий не добавляются.

Проверочный набор обязан покрыть все разрешённые локальные версии `5/7/9/12/13`
и пятнадцать семейств живого инвентаря хотя бы идентичностью и базовой
структурой. Каждая поддержанная позиционная форма обработчика, команды,
атрибута и элемента должна иметь минимум один положительный пример в XML-
контуре или журнале платформенного пробника. Полная приёмка на всех 4 037
формах проверяет отсутствие необъяснённого остатка, но не требует запуска
интерактивного пробника для каждой формы.

### Частичность на уровне формы

Неизвестный тег или позиционная форма не угадывается. Подтверждённые строки
формы сохраняются, неизвестный фрагмент даёт ограниченную диагностику с
кодом, ролью и путём; повреждённый обязательный файл исключает только одну
форму. `parse_form()` возвращает имеющиеся строки. Если строк нет, действует
существующий безопасный `[]`.

### Полная и инкрементальная сборка

Полная сборка вызывает один форматный сборщик. На каждом штатном `update`
источника v8unpack этот же сборщик повторно читает закрытый слой форм и под
одной точкой сохранения полностью заменяет `form_elements`; это повторяет уже
принятый механизм малого JSON-слоя метаданных, работает для игнорируемых Git
файлов и не требует отдельного графа инвалидирования. Ошибка до снятия точки
сохранения оставляет предыдущий слой форм целиком. Изменение
`*Form.obj.bsl` обрабатывает обычный BSL-слой, а `module_path` вычисляется при
чтении по существованию соседнего файла.

Форменная наблюдаемость хранится отдельно от метаданных:

- `v8unpack_form_status`: `complete`, `partial`, `unsupported`, `disabled`,
  `not_applicable`;
- `v8unpack_form_total`, `v8unpack_form_indexed`,
  `v8unpack_form_failed`, `v8unpack_form_unsupported`;
- `v8unpack_form_unproven_fragments`;
- `v8unpack_form_diagnostics_json` с ограниченными агрегированными примерами.

`total` считает каталоги из закрытой матрицы, `indexed` — формы с маркером,
`failed` — формы с отсутствующим/повреждённым обязательным файлом или
нарушением границы корня, `unsupported` — формы с неизвестным контрактом.
Каждый встретившийся тег, позиционная форма или связь, отсутствующие в
доказанном контракте, увеличивают `unproven_fragments` и попадают в
диагностику, даже когда независимые подтверждённые строки той же формы
сохранены.
Для применимого источника выполняется
`total = indexed + failed + unsupported`.

Приёмочный живой инвентарь `tn_bp20_custom_mcp` фиксирует
`total=4037`, `indexed=4037`, `failed=0`, `unsupported=0`;
`unproven_fragments=0`, диагностика неизвестных фрагментов пуста,
`module_path` заполнен у 3 962 форм и пуст у 75 форм без модуля.

### Версия индекса

`BUILDER_VERSION` повышается, поскольку старый индекс версии 17 корректно
считает `form_elements` построенной, но не содержит JSON-строк. Штатное
обновление должно выполнить полную перестройку с прежними флагами.

## Risks / Trade-offs

- [Позиционная сериализация нестабильна] → закрытый реестр версий и парный
  оракул, без выбора «ближайшего» контракта.
- [Часть сведений есть только в `raw`] → поддерживать только доказанные пути,
  а не считать удобные проекции полным источником.
- [Таблица форм может заметно вырасти] → батч-вставка, существующие индексы
  SQLite и приёмочный предел всей сборки `tn_bp20_custom_mcp`: не хуже
  зафиксированных 150 секунд более чем на 20% и не более 512 МиБ полного RSS.
- [Служебная строка меняет число элементов] → считать её только маркером
  присутствия, не включать в handlers/commands/attributes и отдельно проверять
  публичные счётчики.
- [Частичная форма выглядит полной] → публиковать агрегированные счётчики и
  диагностику форм отдельно от общего статуса метаданных.

## Migration Plan

1. Добавить оракул и автономно проверяемые манифесты.
2. Реализовать общий JSON-сборщик и обе ветки индексации.
3. Повысить `BUILDER_VERSION`.
4. Перестроить `tn_bp20_custom_mcp` и проверить `parse_form("АвансовыйОтчет")`.
5. При откате вернуть предыдущую версию пакета и перестроить индекс старым
   построителем.

## Open Questions

Открытых обязательных решений нет. Пользователь выбрал отдельный платформенный
пробник для семантики обычных `Form.bin`; управляемые формы сохраняют
XML↔JSON-контур.
