## Context

XML/MDO-сборщики CF и EDT уже приводят метаданные к таблицам
`object_attributes`, `object_synonyms` и `metadata_references`. У `v8unpack`
объект расположен в отдельном каталоге, UUID вынесен в `.id.json`, а
структурные свойства записаны в позиционном массиве `header`.

Проверенные реальные выгрузки имеют маркер сериализации `1.2.9` и
`obj_version` `802`. Основной дескриптор объекта содержит только `name`,
`name2`, `comment`, `obj_version` и `header`; именованных массивов
`attributes`, `dimensions` или `resources` нет. Поэтому обобщённый обход JSON
или эвристический поиск строк дал бы ложные результаты.

Change выполняется после `add-v8unpack-bsl-source-support`, который предоставляет
`SourceFormat.V8UNPACK` и канонизацию путей BSL.

## Goals / Non-Goals

**Goals:**

- индексировать подтверждённый структурный слой `v8unpack 1.2.9/802`;
- сохранить существующие пользовательские запросы метаданных;
- детерминированно разрешать UUID и ссылочные типы;
- обеспечить равенство полной и инкрементальной индексации;
- отличать полный, частичный и неподдерживаемый разбор;
- не обходить и не индексировать все JSON выгрузки.

**Non-Goals:**

- универсальный декодер всех версий внутренней сериализации 1С;
- `ConfigurationExtension` и метаданные расширений `v8unpack`;
- структурный разбор ролей и прав (имя/UUID роли как цели ссылки разрешены),
  форм, команд, макетов, картинок, MXL, `c1brace`, WSDL, XDTO,
  предопределённых данных и двоичных полезных нагрузок;
- разбор без индекса через файловые запасные ветки хелперов;
- автоматическая распаковка `.cf`, `.cfe`, `.erf` или `.epf`;
- отдельный пользовательский API для `v8unpack`.

## Decisions

### Матрицы первого уровня

индекс уже формирует `object_attributes`.

совпадает с `_CANONICAL_REF_HEADS`; новые цели не добавляются автоматически.

`Configuration.json` даёт `source_format=v8unpack`, `config_name` из `name`,
русский `config_synonym` из `name2`, `v8unpack_metadata_version=1.2.9` и
`config_role=base`. Версия прикладного решения и поставщик не заявляются, пока
их позиционные поля не войдут в отдельное требование.

### Версионный контракт декодера `header`

Рабочий декодер выбирается только для пары
`Configuration.json["v8unpack"] == "1.2.9"` и
`Configuration.json["obj_version"] == "802"`. Иной непустой маркер или иная
корневая версия означает состояние `unsupported`; структурные строки не
создаются. Отсутствующий или повреждённый `Configuration.json` не проходит
предшествующее определение `SourceFormat.V8UNPACK` и остаётся ошибкой
определения формата, а не частичным индексом метаданных.

Каждый основной дескриптор владельца также обязан иметь `obj_version=802`.
Иная или отсутствующая версия владельца обрабатывается как
`unsupported_header_shape` для этого владельца и переводит результат в
`partial`, не блокируя независимые объекты.

До написания производственного декодера создаётся проверяемый контракт
`v8unpack 1.2.9/802` из парных представлений одних объектов в CF XML и
`v8unpack`. Контракт содержит для каждого семейства из матрицы:

- путь к общему заголовку объекта и секции вложенных метаданных;
- UUID-теги поддерживаемых `Attribute`, `TabularSection`, `Dimension` и
  `Resource`;
- позиции UUID, имени, локализованного синонима, типа и дочернего списка;
- отображение примитивных типов и ссылочных UUID в существующую каноническую
  форму;
- эталонные нормализованные строки трёх пользовательских таблиц и отдельные
  пары `(canonical_ref, uuid)` для внутренней `metadata_objects`.

Источником проверки служат реальные фрагменты `header` и XML того же объекта.
Обе стороны получены из одного CF: распаковка выполнена исторической версией
`v8unpack 1.2.9`, а XML выгружен Конфигуратором после загрузки этого CF во
временную файловую базу. SHA-256 проверочного CF:
`413b8d446d748eef99a8972eee0e4bd9a3963b1cc30d1f9ec748104f941a6393`.
`v8unpack` не становится зависимостью
`rlm-tools-bsl`. Синтетический JSON с выдуманными именованными полями не
считается доказательством. При нормализации синонимов завершающие пробелы
удаляются, а удвоенные кавычки приводятся к одной кавычке, как в XML.

Каждый числовой путь и UUID-тег производственного декодера обязан присутствовать
в этом контракте. Неизвестный путь, тег или форма не угадывается:

- неизвестная форма заголовка владельца исключает его структурные строки, но
  сохраняет валидную идентичность как возможную цель ссылки;
- неизвестный вложенный элемент пропускается отдельно;
- неразрешённый UUID типа оставляет атрибут с `attr_type=NULL`, не создаёт
  ложную ссылку и помечает индекс как `partial`.

### Адаптер и двухпроходное разрешение UUID

Форматный адаптер возвращает те же внутренние строки, что XML/MDO-сборщик.
Полная сборка выполняется в два последовательных прохода:

1. прочитать обязательные основной и `.id.json` дескрипторы, сформировать UUID
   объекта → `(category, object_name)` и сгенерированный `TypeId` →
   каноническую ссылку для всей матрицы идентичности;
2. только для структурной шестёрки декодировать `header`, канонизировать типы
   существующим `canonicalize_type_ref` и сформировать синонимы, атрибуты и
   ссылки.

Добавляются две внутренние таблицы:

```sql
CREATE TABLE metadata_objects (
    category TEXT NOT NULL,
    object_name TEXT NOT NULL,
    object_uuid TEXT NOT NULL,
    source_file TEXT NOT NULL,
    PRIMARY KEY (category, object_name)
);
CREATE INDEX idx_metadata_objects_uuid ON metadata_objects(object_uuid);

CREATE TABLE metadata_type_ids (
    id INTEGER PRIMARY KEY,
    type_uuid TEXT NOT NULL,
    canonical_ref TEXT NOT NULL,
    type_form TEXT NOT NULL,
    source_file TEXT NOT NULL,
    UNIQUE (type_uuid, canonical_ref, type_form)
);
CREATE INDEX idx_metadata_type_ids_uuid ON metadata_type_ids(type_uuid);
```

`metadata_objects` хранит UUID из `.id.json`. `metadata_type_ids` хранит
`TypeId` сгенерированных типов (`CatalogRef`, `DocumentRef`,
`InformationRegisterRecordSet` и другие), на которые фактически ссылается
`header` реквизита. Позиции `TypeId` задаются тем же версионным проверочным
контрактом; UUID объекта и `TypeId` не взаимозаменяются.

Повторяющийся UUID сохраняется во всех различных отображениях; разрешение
допустимо только при единственном `canonical_ref`, иначе выдаётся
`unresolved_metadata_uuid`. Существующие
хелперы продолжают читать прежние пользовательские таблицы. XML/MDO-сборщик
эти реестры не использует в этом change.

Для строк из JSON `source_file` и `metadata_references.path` равны основному
`<Kind>.json`, а `metadata_references.line` равна `NULL`: позиционный JSON не
даёт устойчивой XML-подобной строки исходного свойства.

### Белый список файлов

Один классификатор ролей используется сборщиком метаданных, навигацией,
git-дельтой и негитовым снимком:

- корневой `Configuration.json`;
- `<Kind>/<Object>/<Kind>.json`;
- `<Kind>/<Object>/<Kind>.id.json`;

где `<Kind>` входит в матрицу идентичности. Только эти пути читаются и попадают
в `file_paths`; `header` читается только у структурной шестёрки. Общий
`_FILE_NAV_EXTENSIONS` не расширяется на `.json`.

Известные исключённые роли (`*.elem.json`, формы, команды, макеты и двоичные
файлы) не обходятся ради подсчёта и не порождают предупреждение на каждый файл.
Если основной `header` ссылается на известную исключённую грань, она учитывается
агрегированно по UUID-тегу с не более чем пятью отсортированными примерами.
Неизвестный JSON непосредственно в поддерживаемом каталоге владельца даёт
`unsupported_json_role`.

Читаются только обычные файлы, чей разрешённый путь остаётся внутри корня
источника; символические ссылки наружу не обходятся. Размер одного обязательного
JSON ограничен 16 МиБ. Превышение обрабатывается как повреждение обязательного
дескриптора, а не загружается в память.

### Диагностика и наблюдаемая полнота

Результат сохраняется в `index_meta` и включается в существующие сведения об
индексе:

- `v8unpack_metadata_status`: `not_applicable`, `disabled`, `complete`,
  `partial` или `unsupported`;
- `v8unpack_metadata_version`;
- `v8unpack_metadata_identity_total`, `_indexed`, `_failed`;
- `v8unpack_metadata_structural_total`, `_indexed`, `_failed`;
- `v8unpack_metadata_unsupported_count`;
- `v8unpack_metadata_diagnostics_json`.

Для каждой пары счётчиков выполняется `indexed + failed = total`.
`v8unpack_metadata_unsupported_count` равен сумме `count` всех диагностических
групп; одно событие входит ровно в одну группу.

Единица `identity_total` — обнаруженный каталог объекта в любом корне матрицы
идентичности; единица `structural_total` — обнаруженный каталог в структурной
шестёрке. В каждой матрице владелец попадает ровно в один из `indexed/failed`.
Ошибка идентичности структурного владельца делает его одновременно
`identity_failed` и `structural_failed`; это намеренный двойной учёт в разных
метриках, но одно диагностическое событие.

Последнее поле — детерминированно отсортированный JSON-массив не более чем из
50 групп `{code, role, count, examples}`. Ключ агрегации — `(code, role)`,
`examples` содержит не более пяти отсортированных путей. Закрытый словарь:

| `code` | Допустимый `role` | Единица `count` |
|---|---|---|
| `unsupported_v8unpack_version` | `configuration` | один источник |
| `missing_required_json` | `main`, `id` | один отсутствующий файл |
| `malformed_required_json` | `configuration`, `main`, `id` | один повреждённый/слишком большой файл |
| `unsupported_header_shape` | `owner`, `attribute`, `tabular_attribute`, `dimension`, `resource` | один владелец или вложенный элемент |
| `unsupported_header_facet` | UUID-тег грани | один встретившийся элемент исключённой грани |
| `unresolved_metadata_uuid` | `type` | одна строка атрибута с одним или несколькими неразрешёнными компонентами |
| `unsupported_json_role` | `filename` | один неизвестный JSON непосредственно в каталоге владельца |

`examples` всегда содержит путь обязательного/неизвестного файла либо основного
дескриптора, в котором найден элемент. Один исходный факт выбирает наиболее
точный код из таблицы и не дублируется между группами.

`complete` допустим только при поддерживаемой версии и отсутствии пропущенных
владельцев/элементов. `partial` означает, что независимые корректные владельцы
записаны, но хотя бы один обязательный дескриптор, элемент или UUID пропущен.
`unsupported` не создаёт структурные строки. `not_applicable` используется
для CF/EDT. `disabled` используется при `build_metadata=False`: адаптер не
читает структурные JSON, не строит `metadata_objects`, диагностический снимок
и снимок обновления. Навигация по разрешённым JSON строится независимо, если
включён существующий навигационный индекс.

При `build_synonyms=False` остальные JSON-метаданные и идентичности строятся,
`object_synonyms` остаётся пустой, и это само по себе не переводит статус в
`partial`. Оба флага сохраняются и повторно применяются штатным обновлением и
перестройкой.

Повреждённый основной JSON или `.id.json` удаляет все производные строки
владельца при обновлении и оставляет остальные объекты доступными. Это
обеспечивает равенство с новой полной сборкой и исключает устаревшие данные.

### Инкрементальное обновление

Оба пути обновления до фильтра BSL-дельт атомарно заменяют весь JSON-слой под
`SAVEPOINT`: очищают внутренние таблицы и JSON-строки пользовательских таблиц,
повторно обходят только белый список и сохраняют новый снимок
`path`, `owner`, `size`, `mtime_ns`. Это намеренное упрощение: глобальное
UUID-разрешение всё равно требует второго прохода по владельцам, а проверочный
замер полного JSON-прохода укладывается в ресурсные пределы. BSL-слой при этом
не перестраивается.

Полная замена одинаково обрабатывает добавление, изменение, переименование,
удаление и смену UUID и не зависит от доступности истории Git. Старые строки
удаляются до чтения текущего состояния, поэтому отсутствующий или повреждённый
владелец не оставляет устаревших данных, а независимые владельцы восстанавливаются
в той же транзакции.

Изменение, удаление, повреждение или исправление корневого
`Configuration.json` атомарно очищает и заново формирует весь JSON-слой:
`metadata_objects`, `metadata_type_ids`, JSON-строки трёх пользовательских
таблиц, диагностику и снимок владельцев. BSL-слой не перестраивается. Отдельные ключи
`v8unpack_metadata_last_root_size`, `v8unpack_metadata_last_root_mtime_ns` и
`v8unpack_metadata_recovery_pending` не удаляются вместе со снимком.

При обновлении ранее сохранённые `source_format=v8unpack` и снимок являются
основанием выполнить очистку, даже если повреждённый текущий
`Configuration.json` теперь определяется как `UNKNOWN`. В таком случае
JSON-строки удаляются, статус становится `unsupported`, а диагностика содержит
`malformed_required_json`. После исправления формат снова определяется как
`V8UNPACK`. Любое обновление до обычного фильтра дельт проверяет
`recovery_pending`; если live-формат снова `V8UNPACK` и статус был
`unsupported`, снимок отсутствует либо `recovery_pending=1`, выполняется
безусловный полный refresh JSON-слоя, снимок создаётся заново, а флаг
сбрасывается. При чистой сборке
отсутствующий или повреждённый корневой файл остаётся `UNKNOWN` согласно
существующему определителю и JSON-адаптер не запускается.

### Миграция, откат и совместимость

`BUILDER_VERSION` повышается до `16`. Штатная проверка несовпадения версии
принудительно перестраивает старый индекс и сохраняет исходные флаги сборки.
Миграция «на месте» не выполняется: старые индексы не содержат достаточных
данных о JSON.

Откат на предыдущую версию требует штатной полной перестройки предыдущим
исполняемым файлом. Пользовательские таблицы CF/EDT и их запросы не меняют
смысл.

### Производительность

Сборщик перечисляет только корни матрицы идентичности и фиксированные имена
файлов, не делает `rglob("*.json")` и не удерживает DOM нескольких владельцев
одновременно. Сложность равна `O(число владельцев + размер поддерживаемых
дескрипторов)`.

Приёмочный предел на предоставленных малой и большой реальных выгрузках:
медиана трёх прогонов фазы JSON не более 120 секунд, дополнительный пик RSS не
более 512 МиБ, число открытых JSON равно белому списку. Эти пределы не заменяют
семантическую сверку с XML.

## Risks / Trade-offs

- [Позиционный формат изменится] → жёсткий выбор `1.2.9/802`, отказ без
  эвристики и отдельный контракт для новой версии.
- [Частичный результат примут за полный] → статус и диагностика в существующих
  сведениях об индексе.
- [UUID изменился, а ссылки устарели] → двухпроходная сборка и повтор ссылочного
  прохода при изменении идентичности.
- [Все JSON попадут в обход или навигацию] → общий точный классификатор ролей.
- [Повреждение оставит старые строки] → атомарная полная замена владельца и
  проверка равенства с чистой сборкой.
- [Проверки подтвердят только самосогласованность декодера] → обязательный
  XML↔JSON семантический оракул.

## Migration Plan

1. Зафиксировать проверочный контракт `header` на парных XML↔JSON объектах.
2. Добавить версию схемы, внутренний реестр UUID и диагностические поля.
3. Реализовать адаптер и двухпроходную полную сборку.
4. Подключить общий классификатор к навигации и обоим путям обновления.
5. Доказать семантический паритет с XML и равенство полной/инкрементальной
   сборки на добавлении, изменении, удалении и переименовании.
6. Выполнить регрессию CF/EDT и приёмочные замеры.
